# CAN OTA 设计文档（三节点 IAP over CAN）

> 日期：2026-09-29
> 范围：把已有的 UART IAP Bootloader 合并进三节点 CAN 项目，实现「PC → 主控 → CAN → 节点」的可运行 OTA。
> 状态：设计已与作者逐节确认，待评审后进入实现计划。

---

## 0. 背景与目标

### 0.1 起因

面试官看过项目后提了两点：

1. 三节点（一主两从）有点多余，认为一颗 F407 就能实现同样的功能；
2. 建议把 Bootloader 加进三节点项目，做成一个更大的完整项目。

### 0.2 我们对第 1 点的判断

先承认对方对的部分：**如果目标只是“读一个传感器 + 驱动一个电机”，一颗 F407 确实更简单、更便宜、故障点更少**，加两个节点属于为功能硬凑。

但我们决定**保留三节点**，理由是分布式系统买到的能力单 MCU 给不了：

- **省线**：传感器/执行器离得远时，只拉一根两线 CAN 总线，而不是把一堆信号线拉回主控；
- **可扩展**：加节点不影响主控；
- **故障隔离**：一个节点掉线，其他节点照常运行——本项目已实现（心跳 + 离线检测 + 恢复）；
- **本地实时**：电机节点自己跑 20ms PID 闭环，主控不背这个负担。

**关键教训**：三节点本身没问题，问题是“没讲清为什么用它”。因此本项目要在文档和演示中明确、甚至演示“分节点买到了什么”。

### 0.3 本次目标

做一个**能真正跑起来的 CAN OTA**，并形成一个链路完整、面试可讲的大项目；
同时保留后续扩展空间（版本管理/回滚、Linux 项目）。

---

## 1. 设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 节点架构 | 保留三节点 | 分布式系统价值 + 已实现的故障隔离 |
| 升级通道 | CAN 总线 | 贴近真实的工业/车载 OTA，比 UART 有分量 |
| 固件入口 | PC ─UART→ 主控 ─CAN→ 节点 | 主控承担 OTA 服务器，链路完整 |
| 主控自升级 | 沿用已有 UART IAP | 主控既是服务器就不必自己刷自己，逻辑最干净 |

---

## 2. 关键约束（实测）

1. **F103C8T6 只有 64KB Flash**。实测当前 APP 体积（Debug 构建）：
   - 传感器节点 `text+rodata+data` ≈ **34.6KB**（0x080086C4）
   - 电机节点 ≈ **36.4KB**（0x08008E44）
   - Release 构建会更小。结论：Bootloader(8KB) + APP 装得下，约剩 20KB 余量。
2. **擦写方式不同**：F103 是**页擦除（1KB/页）+ 半字（16 位）编程**；F407 是**扇区擦除 + 双字（64 位）编程**。两套 Flash 驱动必须分开写。
3. **CAN 一帧只有 8 字节**：固件必须分帧传输，UART 那套 256 字节变长帧不能直接搬。
4. **APP 要能切回 Bootloader**：节点正在跑 APP 时无法直接升级，需要一个“进入升级”的机制。

---

## 3. 总体架构与角色

| 角色 | 平时 | 升级时 |
|---|---|---|
| PC 上位机（Python） | —— | 选目标节点、读固件、经 UART 下发；显示进度 |
| F407 主控 | 心跳/命令/故障监控（现有） | 作 CAN OTA 服务器：收固件 → 暂存 → 发起 CAN 升级 → 收集进度 → 回报 PC |
| F103 节点 | 跑业务（传感器/电机） | 收到“进入升级” → 复位进 Bootloader → 经 CAN 收固件 → 写 Flash → 校验 → 重启 |

**两条升级入口**：

- 主控自升级：`PC ─UART→ F407 Bootloader`（复用已有 IAP，不改）
- 节点升级：`PC ─UART→ F407 APP ─CAN→ 节点 Bootloader`（本次新增）

## 4. Flash 分区与地址

### 4.1 F407 主控（1MB，扇区式擦除）——保持不变

| 区域 | 地址 | 大小 |
|---|---|---|
| Bootloader | 0x08000000 | 64KB（Sector 0-3） |
| APP | 0x08010000 | 960KB |

节点固件约 36KB，主控用 **SRAM 缓冲区**暂存（F407 有 128KB+ SRAM），**不改 Flash 布局**。

### 4.2 F103 节点（64KB，页式擦除）——新增分区

| 区域 | 地址 | 大小 |
|---|---|---|
| Bootloader | 0x08000000 | 8KB（8 页，含 CAN 接收 + 帧处理 + Flash 驱动） |
| APP | 0x08002000 | 56KB |

若 Bootloader 用 HAL 编译后超过 8KB，退到 16KB（APP 从 0x08004000 起，48KB）——按实际编译结果定。

### 4.3 APP 必须新增的两处

- `SCB->VTOR = 0x08002000;`（向量表随分区搬移，否则中断跑飞）
- APP 有效性标志 `magic` 放在 `0x08002100`（APP_START + 0x100），与主控方案一致

## 5. CAN OTA 帧协议

### 5.1 帧 ID 分配（用硬件过滤器寻址）

| 帧类型 | Node1 | Node2 | 方向 |
|---|---|---|---|
| 控制帧 | 0x300 | 0x310 | 主控 → 节点 |
| 数据帧 | 0x301 | 0x311 | 主控 → 节点 |
| 应答帧 | 0x302 | 0x312 | 节点 → 主控 |

> 0x3xx 优先级低于现有 0x100/0x2xx，OTA 传输不会抢占心跳和命令帧（有意为之）。

### 5.2 控制帧（data[0]=命令）

| 命令 | 含义 | 参数 |
|---|---|---|
| 0x01 | ENTER 进入升级 | 无 |
| 0x02 | ERASE 擦除 | data[1..2] = 镜像总长（2B 小端） |
| 0x03 | FINISH 结束校验 | data[1..2]=总长，data[3..6]=CRC32（4B 小端） |
| 0x04 | REBOOT 重启 | 无 |

> 长度用 2 字节（≤65535）：F103 的 APP 最大 56KB，够用；UART 侧用 4 字节是因为主控镜像 960KB。两个协议按各自容量选长度字段。

### 5.3 数据帧

`序号(2B 小端) + 数据(6B)`，序号从 0 起；节点按 `地址 = APP_START + 序号 × 6` 写入。

### 5.4 应答帧

`状态(1B) + 关联序号(2B 小端)`。状态码：

| 状态码 | 含义 |
|---|---|
| 0x06 | ACK |
| 0x15 | NACK |
| 0x01 | BOOTLOADER_READY |
| 0x02 | ERASE_DONE |
| 0x03 | FINISH_OK |
| 0x1F | ERROR |

### 5.5 可靠传输

- 主控每发一帧等 ACK，超时（约 50ms）重传，重试 3 次仍失败则终止并报 PC；
- **单帧不加软件 CRC**（CAN 硬件有 CRC 保护单帧）；只在最后做一次**整包 CRC32**（复用 `bl_crc.c`）防漏帧/乱序；
- 量级估算：36KB ÷ 6B ≈ 6100 个数据帧，500kbps 下纯传输几秒，含 ACK 往返与 Flash 写入预计几十秒。

## 6. 升级流程

```text
PC ─UART─→ 主控APP              主控 ─CAN─→ 目标节点Bootloader
  1. 下发固件(节点号+总长+CRC)；主控收齐、暂存SRAM、校验CRC
  2. ENTER ─────────────────────→ 节点APP置BKP标志 → 复位
  3.                              Bootloader进升级态 → 回 READY
  4. ERASE(总长) ───────────────→ 擦除 → 回 ERASE_DONE
  5. DATA(序号+6B) ⇄ ACK ──────→ 写Flash   （循环）
  6. FINISH(总长+CRC) ──────────→ 重算整包CRC → 通过写magic → 回 FINISH_OK
  7. REBOOT ────────────────────→ 复位 → 跳新APP
  8. 主控把结果回报PC
```

**进入升级机制**：节点 APP 收到 ENTER 后，把标志写入 **BKP 备份寄存器**（复位不清零），再 `NVIC_SystemReset()`；Bootloader 上电读 BKP，有标志进升级态，否则检查 APP 有效性并正常跳转。（备选：`.noinit` RAM 区。）

**失败保护**：

- FINISH 校验不过 → 不写 magic → 下次上电判 APP 无效 → 停在升级态等重升，**不跑坏固件**；
- 升级中途掉电 → APP 区不完整但 magic 未写 → 可重升，**不变砖**；
- 丢帧/超时 → 重传 3 次仍失败 → 终止报错，节点停在 Bootloader 等待；
- 不影响其他节点 → ID + 硬件过滤，只有目标节点收帧。

## 7. 上位机与主控改动

### 7.1 PC 端

复用现有 `upgrade_tool.py`（主控 UART IAP，不改）；新增节点 OTA 工具：

```text
python ota_tool.py COMx master app.bin    → 现有 UART IAP
python ota_tool.py COMx node1  node1.bin  → 经主控，CAN 升级 Node1
python ota_tool.py COMx node2  node2.bin  → 经主控，CAN 升级 Node2
```

PC ↔ 主控沿用现有 UART 帧格式 `A5 5A | CMD | ADDR | LEN | DATA | CRC32`，新增命令：

| 命令 | 含义 | 载荷 |
|---|---|---|
| 0x10 | OTA_BEGIN | 目标节点(1B) + 总长(4B) + CRC32(4B) |
| 0x11 | OTA_DATA | 256B 分块 |
| 0x12 | OTA_QUERY | 查询进度 |

**流程**：PC 先发完整固件 → 主控暂存并校验 → 再开始 CAN OTA。不做流式传输（36KB 规模无收益）。

### 7.2 主控 APP 新增三样

1. **UART 接收任务 + 命令解析器**（现有主控只有 printf 发送，没有收）；
2. **SRAM 固件缓冲区**（约 40KB）；
3. **CAN OTA 状态机**（发 ENTER/ERASE/DATA/FINISH/REBOOT，管重传与超时）。

## 8. 测试与验证方案

**模块级**
- F103 Flash 驱动：页擦除 + 半字写，写后读回比对；
- CAN 分帧/解帧：序号、6 字节拼装、尾帧不足 6 字节的边界；
- 整包 CRC：PC 与 F103 结果一致（标准向量 0xCBF43926）。

**链路级**
- PC→主控 UART 整包传输 + CRC 校验；
- 主控→节点五个阶段逐段验证；
- 节点 Bootloader 写 Flash → magic → 跳新 APP。

**异常与边界**
- 丢帧/超时 → 重传；连续失败 → 终止报错；
- 固件改坏 1 字节 → FINISH NACK、不写 magic、可重升；
- 升级中拔电源/总线 → 重上电不变砖；
- 升级 Node2 时 Node1 照常运行（不误收）；
- 心跳/业务帧同时存在时 OTA 正常。

**成功判据**
- 新固件带可区分版本标识（慢闪/快闪或串口打印版本号）；
- 连续升级 N 次稳定。

**可观测性与证据**
- 主控串口打印各阶段与进度；PC 端显示进度；
- CAN 分析仪抓 OTA 帧截图存档；
- 输出一份测试记录。
