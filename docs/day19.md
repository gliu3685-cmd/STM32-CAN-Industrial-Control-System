## 2. 理论学习（Theory）

### 2.1 心跳机制（Heartbeat）

工业现场主控判断从机是否存活的通用手段是心跳：每个节点周期性上报一帧状态，主控只要在约定时间内持续收到就认为节点在线，超时未收到则判离线。这与硬件看门狗同源，本质都是"用超时替代直接测量"。

本系统三节点天然构成心跳结构：

| 帧 ID | 方向 | 周期 | 内容 |
|---|---|---|---|
| 0x100 | F407 主控 → 总线 | 1s | 心跳帧（seq + 状态字） |
| 0x102 | Node1 传感器 → 主控 | 1s | 温度数据 |
| 0x202 | Node2 电机 → 主控 | 1s | 速度数据 |

### 2.2 数据新鲜度（Data Freshness）

"节点在线"的本质是"数据新鲜"：主控记录每个节点最近一次收到帧的时间戳 `last_rx_tick`，周期检查 `now - last_rx_tick` 是否超过阈值（协议约定 5s）。

```text
收到帧  ──>  更新 last_rx_tick[i] = 当前 tick，node_online[i] = 1
周期检查  ──>  (now - last_rx_tick[i]) > 5000ms ? 判离线
```

节点 1s 发一帧，5s 超时窗口意味着允许漏约 3~4 帧，兼顾"不误报"与"及时告警"。

### 2.3 故障注入（Fault Injection）

故障注入是嵌入式/汽车电子（ISO 26262）测试的必修课：故意制造故障，验证系统能否及时检测、不误报、自动恢复。本日采用最朴素的硬件注入——拔线、断电、插回。

### 2.4 CAN 错误处理

* **ACK 错误（LEC=3）**：CAN 帧末尾有应答槽，发送方必须看到至少一个节点拉低应答；总线无人应答时报 ACK 错误。
* **LEC（Last Error Code）**：ESR 寄存器中最近一次错误的类型编码（0=无，1=填充，2=格式，3=应答，4=位隐性，5=位显性，6=CRC）。
* **TEC/REC 错误计数器**：发送错误 +8、接收错误 +1（特殊情形 +8）、成功后递减；TEC≥256 进入总线关闭（Bus-Off）。

## 4. CAN 应用层协议（Protocol）

三节点总线协议采用 11 位标准帧，固定 ID 分配如下：

| 帧 ID | 方向 | DLC | 数据负载（字节序：小端） | 周期 |
|---|---|---|---|---|
| 0x100 | F407 主控 → 总线 | 8 | [0]=seq 低字节，[1]=seq 高字节，[2]=0x55，[3]=0xAA，[4..7]=预留 0 | 1s |
| 0x101 | 主控 → Node1 | — | 预留命令帧（尚未使用） | — |
| 0x102 | Node1 → 主控 | 2 | [0]=温度低字节，[1]=温度高字节（恒 0） | 1s |
| 0x201 | 主控 → Node2 | — | 预留命令帧（尚未使用） | — |
| 0x202 | Node2 → 主控 | 2 | [0]=速度低字节，[1]=速度高字节 | 1s |

过滤与映射约定：

* 主控 F407：Bank0 精确收 0x102，Bank1 精确收 0x202（掩码模式，Mask=0x7FF 全比较）
* Node1 只收 0x101，Node2 只收 0x201（各自命令帧）
* 主控应用层映射：`0x202 → 节点号 1`，其余（0x102）→ 节点号 0

## 5. 离线检测代码（已有，Day18 实现）

`app_arch.c` 的 `FaultMonitorTask` 每个心跳周期（1s）检查数据新鲜度，超过 5s 判离线；仅在状态翻转时打印一次告警，恢复上报后自动回到在线。

```c
now = xTaskGetTickCount();
xSemaphoreTake(xSysMutex, portMAX_DELAY);
for (i = 0; i < ARCH_NODE_NUM; i++) {
    if ((now - gSys.last_rx_tick[i]) > ARCH_RX_TIMEOUT_MS) {
        if (gSys.node_online[i] == 1U) {
            ArchPrint("[FAULT] node%u offline detected!\r\n", (unsigned)i);
        }
        gSys.node_online[i] = 0;
        offline = 1;
    }
}
xSemaphoreGive(xSysMutex);
```

## 6. 实验过程（Experiment）

### 实验 A：Node1 拔线离线

拔掉 Node1 的 CANH 线。

现象：F407 串口约 3s 出现 `[FAULT] node0 offline detected!`，PCAN-View 里 102h 消失，100h/202h 正常。

验证：节点离线检测在 5s 阈值内触发；单节点脱离总线不影响其他节点通信。

### 实验 B：Node2 拔线离线

拔掉 Node2 的 CANH 线，出现 `[FAULT] node1 offline detected!`，102h 消失。验证成功。

### 实验 C：Node1 断电

不拔线，直接断开 Node1 供电。现象与实验 A 一致，验证成功——拔线与断电在主控视角等价（都是"帧不来了"）。

### 实验 D：主控拔线（总线无人应答）

拔掉 F407 主控自己的 CANH。

现象：PCAN-View 里 100h 消失；主控串口打印 `[CAN_ERR] LEC=3 TEC=0 REC=40`；随后 `[FAULT] node0 offline detected!` 与 `[FAULT] node1 offline detected!` 相继出现。

验证：

* `LEC=3` 是 ACK 错误——主控发 0x100 时总线无人应答
* 主控自身物理层断开，收不到两从节点帧，5s 后两个节点一起判离线
* 对比实验 A/B：单节点离线只报该节点；主控/总线故障则"全离线 + 主控报 ACK 错误"，据此可实现故障定位

## 7. 遇到的问题与解决（Problems & Solutions）

### Problem 1：实验 D 中 TEC=0 而 REC=40

问题：主控拔 CANH 后报 ACK 错误（LEC=3），按规则 ACK 错误通常应使 TEC 增加，但观察值为 TEC=0、REC=40。

原因：REC 增长来自主控接收侧——主控 CANH 断开后，接收仍连着的 Node1/Node2 帧时差分信号畸变，检测出接收错误，REC 累积到 40。TEC 为 0 说明发送侧错误未按预期累积，可能因为 CANH 断开时发送帧在更早位就已 bit error、或采样时刻在错误被动阈值之前。

结论：核心证据（LEC=3 = ACK 错误 + 双节点离线）足以支撑故障定位结论；TEC/REC 的精确时序需抓取完整 ESR 变化，留作后续进阶课题，不影响本日结论。

## 9. 工程总结（Engineering Summary）

## 心跳与看门狗同源

节点在线检测不依赖电气测量，而是"超时未收到帧即离线"。这与任务看门狗、硬件看门狗同属一个思想：用超时替代直接测量，简单可靠。

## 故障定位靠交叉信息

单节点离线与主控/总线故障的表象都是"帧收不到"，但主控是否同时报 ACK 错误是关键的区分信号，据此可以缩小故障范围。

## 10. 面试问答（Interview Prep）

### Q1：心跳超时为什么设 5s 而不是 500ms？

答题要点：

* 太短会因调度抖动、瞬时干扰丢帧而误报
* 太长则故障发现慢
* 工业上常取发送周期的 3~5 倍（本系统 1s 发送 × 5）

### Q2：主控如何区分"节点坏了"和"总线断了"？

答题要点：

* 单节点离线：只有该节点超时，主控自身收发正常、无 ACK 错误
* 总线/主控故障：所有节点一起离线，且主控自己发帧报 ACK 错误（LEC=3）、错误计数器增长
* 靠这些交叉信息实现故障定位

### Q3：什么是数据新鲜度？为什么比"收到就算数"更重要？

答题要点：

* 用时间戳判断数据是否过期
* 收到旧数据比收不到更危险，可能让系统按过期状态做出错误决策
* 闭环控制中，过期反馈比无反馈危害更大

### Q4：CAN 错误计数器机制？

答题要点：

* 发送错误 +8、接收错误 +1（特殊情形 +8）、成功后递减
* TEC≥128 进入错误被动，TEC≥256 进入总线关闭（Bus-Off）
* `AutoBusOff=ENABLE` 后硬件自动恢复，恢复前需 128 个隐性位
